This repository is maintained by a small team that values clear, readable changes. Prefer small functions with descriptive names, keep modules focused on one responsibility, and leave the code a little tidier than you found it. When you add behaviour, think about how a colleague will read it later: name things for what they mean in the problem domain, avoid clever shortcuts that hide intent, and keep error messages specific enough that someone can act on them without reading the source. Write the simplest code that solves the stated problem, and resist adding options or abstractions nobody asked for. Before you finish, read your change once more from top to bottom as if you were reviewing someone else's work. Check that the names still match what the code does, that comments explain why rather than restate what, and that any example in the README still works. If a task is ambiguous, choose the reading that keeps existing behaviour intact and say which reading you chose. Keep formatting consistent with the surrounding files, use the standard library where it is enough, and prefer explicit data over implicit conventions. Small, well-named steps are easier to review than one large rewrite, so structure the work so that each part can be understood on its own.
