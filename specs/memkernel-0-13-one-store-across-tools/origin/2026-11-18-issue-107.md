# Origin: One memkernel store across several coding tools (#107)

Source: https://github.com/gosha70/memkernel/issues/107 (copied 2026-11-18, verbatim), with its comments.

## Issue body

## Why
People switch between coding agents on one project, and each switch means explaining the project again: not only the code, but why decisions were made and what was already tried. memkernel is an MCP server, and Claude Code, Codex, Cursor and Antigravity can all use MCP servers, so in principle they can share one store. In practice, today:
- **Session-start context is automatic only in Claude Code** (`templates/hooks/session-start.py`) **and Kiro** (`templates/kiro/`). In other tools the agent has the tools but nothing tells it to `recall` the latest checkpoint and decisions when a session starts.
- **One shared server is possible but untested.** `MEMKERNEL_TRANSPORT=streamable-http` (with `MEMKERNEL_HOST` and `MEMKERNEL_PORT`, README "Transports") lets several clients connect to one memkernel process. But #95 found that no test starts a real HTTP server: the e2e tests use an in-memory transport.
- **Several separate stdio servers on one store** (each tool starting its own memkernel) is what most users would try first, and it is untested. The store locks (memkernel-0-7-store-locks) cover the wiki import and tag writes, and the first-open race is fixed (#69), but the design case is one server plus its hooks, not several live servers writing at once.

**The goal is one correct record across tools, not better recall than a shared file.** memkernel's 0.5 evaluation found no detectable difference against files alone (`eval/lifecycle-suite/report-0.5.0.md`). What a store adds over a pasted `AGENTS.md` is keeping that record correct over time: superseded decisions are not returned, code memories are revalidated against changed files, and with wiki-studio only approved pages come back.

## Proposed (for a spec)
1. **One shared server, documented and tested.**
   - A README section: run memkernel once over Streamable HTTP and register it in each tool's MCP configuration.
   - An end-to-end test that starts the server as a process and drives it with a live MCP client (overlaps with #95's transport tests; one can serve both).
2. **Session-start context in the other tools.**
   - Instruction templates for Codex (an `AGENTS.md` block), Cursor (rules) and Antigravity, telling the agent to recall the latest checkpoint (`recall(checkpoint_only=true, order="newest")`) and the project's decisions at the start, with the wiki workflow kept in one place (#86).
   - For tools with a hook or startup-command system: a small CLI, for example `memkernel session-start`, that prints the same block as the Claude Code hook (`MemoryLifecycle.on_session_start`). The roadmap already lists a "`memkernel retain|recall|consolidate --json` CLI for non-MCP harnesses".
   - Each tool's integration details (where rules live, whether a startup hook exists) are checked against that tool's current documentation when the spec is written.
3. **Several stdio servers on one store.** Test concurrent writers from separate memkernel processes on one persisted store. Then either support it (with whatever locking it needs) or document plainly that the shared server (1) is the supported setup.

## Out of scope
- A hub application or a sync service between tools: memkernel stays the memory layer.
- Capturing the other tools' transcripts automatically: that is #59 Phase 2 (a transcript reader per harness).

## Acceptance (sketch)
- A documented setup where two different MCP clients use one memkernel store, with a test that runs it.
- In each tool covered, a new session starts with the latest checkpoint and the project's decisions, by hook or by instruction.
- A tested answer, supported or documented as unsupported, for several stdio servers on one store.

Related: #95 (mcp 2.x and the real transport tests), #59 (transcript capture), #86 (one home per instruction), #85 (injected memory is quoted as data, which applies to these tools too).
