# Plan: memkernel 0.6 — the Release B wiki bridge

## Why now, and the constraint
wiki-studio's "memkernel Release B loop" CI job is red (non-blocking, `continue-on-error`) until memkernel #48
lands. memkernel-0-5 FR-017 requires `check_freeze.py` to pass between the freeze (641a508) and the `v0.5.0`
tag. Since 2026-10-27 `main` holds #53 (this spec) and #56 (the arm pin), which are outside its allowlist, so
the tag can no longer be cut from `main` (owner decision 2026-10-27, option B):
- `release/0.5` is created from the preregistration merge `8674480` and carries only allowlisted commits: the
  measured run's `results/`, `report-0.5.0.md`, `README.md`, `CHANGELOG.md` and the two version lines.
- `python eval/check_freeze.py 641a508a2289b2d20775e6d149a0bb47678d1621` is run on `release/0.5` and must pass
  before `v0.5.0` is tagged there; then `release/0.5` is merged into `main`.
- The report discloses that `main` carried non-allowlisted changes before the tag, kept off the tagged commit.
- CI does not cover `release/0.5`: `ci.yml` runs only for pushes to `main` and PRs into `main`, and it cannot be
  changed there (not on the allowlist); `release.yml` runs on the tag but only checks the tag against the
  version, builds, smoke-tests the wheel and publishes. So on `release/0.5`, before tagging, these run locally
  and their output goes into the release PR description and the report: the report regenerated byte for byte
  from the committed receipts, the secret scan of the committed results, `check_freeze.py`, and the version
  bump from `0.5.0rc1` to `0.5.0` in both version files (only their version line).
With the tag no longer on `main`, spec and code PRs for this feature may merge to `main` once reviewed; code
PRs still wait for the tag so `v0.5.0` and `0.6` stay distinct releases.

## Approach
Two parts, because part of Release B needs a wiki-studio release that does not exist yet:
- **Part 1 (US1–US2, buildable now against wiki-studio 0.6.0):** remove `_WikiSnapshot`, scaffold through
  `api.init`, require wiki-studio ≥ 0.6.0 for the gate, record each export's proposal receipt, and pass the
  combined gate's compatibility and concurrency tests.
- **Part 2a (US3–US4, specified 2026-10-27 against wiki-studio 0.7.0):** approved-only import through
  `api.review_state`, the `corrects` grammar and reconciliation; one floor of 0.7.0 for both parts. Its acceptance
  test is wiki-studio's own `tests/integration/test_release_b_loop.py`, which drives memkernel: against part 1
  (#55) its two retry tests pass and its four loop tests fail on the importer (baseline 2026-10-27).
- **Part 2b and 2c (not specified yet):** withdrawal with a sync state; governed configuration and curation debt.

The tests target the bridge's API surface (`propose`, `promote`, `init`, `read_page`), which wiki-studio keeps
unchanged for the bridge in 0.7.0 (owner decision 1, memkernel #48 comment of 2026-10-24); moving the dev lock
from 0.6.0 to 0.7.0 when it is published should need no test change.

## Files (part 1)
`src/memkernel/wiki/sync.py`, `src/memkernel/wiki/studio.py`, `pyproject.toml`, `poetry.lock`,
`docs/adr/ADR-010-wiki-studio-as-wiki-maintainer.md` (addendum), `README.md` (wiki section), `CHANGELOG.md`,
`tests/unit/test_wiki_studio.py`, a new `tests/integration/test_wiki_studio_gate.py`.

## Risks
- Without the snapshot, a failed gated export relies on wiki-studio's own rollback and receipts. That is only
  safe from 0.6.0 on, hence the floor and the refusal of older versions (FR-003).
- A new wiki scaffolded by `api.init` differs from memkernel's direct-writer scaffold, so memkernel-0-5's SC-2
  byte-identity no longer holds for the scaffold of a new wiki (FR-002); pages and appended lines stay identical.
  A failed export now leaves that scaffold in place (FR-001). Both are user-visible and go in the CHANGELOG.
- wiki-studio 0.6.0 can commit an export and fail to archive it; the receipt then stays in the proposals
  directory. FR-005 reads it there and reports "promoted, not archived" (SC-6).
