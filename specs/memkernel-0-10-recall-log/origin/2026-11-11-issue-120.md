# Origin: Make repeated mistakes countable: a recall log and a counting script

Source: https://github.com/gosha70/memkernel/issues/120 (copied 2026-11-11, verbatim)

## Issue body

## Why
On #112, an outside question asked whether repeated mistakes have ever been counted on memkernel sessions: a failure coming back in a later session after it was already stored. A hand count on one real build, using a fixed rule, was posted there (the GeorgeIvan comment). Asked whether the rule exists as a script others could rerun, the answer is that none is published.

The rule has three steps, and memkernel can supply only the first:
1. **Memories the agent stored that quote an error message:** in the store, so memkernel can list them.
2. **A later session whose own command output contains that message:** not in memkernel. Command output lives in the coding tool's session logs, such as Claude Code's transcript files.
3. **Whether a `recall` returned that memory in the session, before the failure:** not recorded. memkernel only counts accesses (`access_count`), with no per-call log of what `recall` returned.

There's also a linking problem. The MCP server never sees the coding tool's session id, so a memkernel record can't name the session it belongs to. The session spool from memkernel-0-7-hooks already records each Claude Code session's start and end, so its windows can map a timestamp to a session.

## Proposed (for a spec)
1. **A recall log.** Each `recall` appends one record: time, query, filters, and the returned `ref_id`s in order.
   - Stored under `MEMKERNEL_STATE_DIR`, next to the sync ledger and the session spool. Local only, never in git.
   - **Off by default**, enabled by a new setting such as `MEMKERNEL_RECALL_LOG=1`, because it stores queries, which can contain project text. Documented in the README's configuration table.
   - Bounded, by size or age, like the spool's pruning.
   - No change to `recall`'s results or to the MCP tools.
2. **A counting script** in `eval/`, for example `eval/repeat-mistakes/count.py`, that applies the #112 rule:
   - reads the store's memories that quote an error message;
   - reads the coding tool's session logs (Claude Code transcripts first) for each later session's own command output, never notes or documents that merely mention the message;
   - maps sessions through the spool's windows, and reads the recall log;
   - classifies each repeat: memory returned before the failure, in the store but not returned (a retrieval miss), or not in a store that session could read.
   - The output states its limits: exact-text matching misses reworded errors.
3. **Reading session logs** overlaps with #59 Phase 2 (a transcript reader for each tool). The script should use that reader once it exists, and until then keep its own small Claude Code reader, documented as temporary.

## Out of scope
- A "mistake" memory type, or any automatic correction.
- Judging "the same mistake" with a model: the rule stays mechanical.
- Changing what `recall` returns.

## Acceptance (sketch)
- With the log enabled, every `recall` leaves one record. With it disabled, nothing is written.
- The script, run on a fixture with known repeats (one returned before the failure, one retrieval miss, one memory in an unreadable store), reports each in the right class.
- A README section explains how to run the count on your own build, and what it can't detect.

Related: #112 (the question and the hand count), #59 (transcript reader), #107 (separate stores across roles or tools, which caused three of the five counted repeats), #57 (a replay corpus, which could also measure retrieval misses on error text).

## The counting rule, as posted on #112

Source: https://github.com/gosha70/memkernel/issues/112 (GeorgeIvan, 2026-11-08, quoted)

  How "the same mistake" was judged: mechanically, with no judge, by a rule fixed before the count was run.
  - A memory the agent stored that quotes an error message.
  - A later session whose own command output contains that message. Reading a note or document that mentions it doesn't count.
  - Each repeat classified by what that session could see: whether its store held the memory, and whether a recall returned it before the failure.
