# Origin alignment check — memkernel-0-4

Origin: https://github.com/gosha70/memkernel/issues/9 and https://github.com/gosha70/memkernel/issues/10 (both read in full this session), with the user's plan-phase decisions in specs/memkernel-0-4/origin/2026-10-12-decisions.md; issue #3's closing comment records the deliberate non-choices.

Origin claim:
> Start working on the two issues left after closing #3 as superseded: #9 revalidate `code` memories when their source changes (mark `needs_review`, exclude from default recall, supersede on re-retain, no LLM or new dependency, plain file hashing) and #10 a deterministic, LLM-free store health pass (orphans, dangling links, stale sources, near-duplicates, expired-but-present; read-only, no new MCP tool). Ship both as one bundle, version 0.4.0; run revalidation through consolidate(revalidate=...) and at session start; auto-supersede code memories by source; expose health through Python, the admin API, the status resource and the consolidate report.

Working claim:
> spec.md delivers four user stories: (US1) `MemoryService.revalidate()` compares each live canonical `code` memory's file hash with its `content_hash` under a new `project_root` setting, inside a resolved-path boundary (symlinks and `..` handled; outside paths are `unknown` and never read), flags `needs_review` with reason `changed` or `missing` (clearing it when the file matches again), propagates to owned chunk records only, excludes flagged memories from `recall` unless `include_needs_review=True`, runs from `consolidate(revalidate=True)`, from `MemoryLifecycle.on_session_start()` (new `### Needs review` section only when non-empty) and from `POST /revalidate`; (US2) sourced `code` identity becomes `(source, content_hash)` (`find_by_hash` gains a `source` filter), chunk records of `code` memories become owner-specific (`<canonical>-chunk-<n>`, `code_chunk` tag, `parent_ref`, no content dedup), and `retain(type=code, source=X)` with changed content sets `supersedes` on the new canonical and a durable `superseded_by` on every live old canonical for `X`, deletes only their owned chunk records, keeps the old canonicals, and `_filter_live`, `list_memories`, `consolidate` and `WikiExporter` treat a `superseded_by` record as superseded regardless of the fetched set, while unmarked 0.2/0.3 links are reported by health as `unmarked_supersessions` for a later fix mode; `find_by_hash` never returns a chunk record and a dedup hit embeds nothing; identical content under the same path still dedups and under another path is its own record; (US3) a read-only `health(full=True)` returning `HealthReport` with orphans (document parts, tagged code chunks), dangling links, unmarked supersessions, stale sources (`code` only; document sources are names), needs-review, expired-but-present and, in full mode only, near-duplicates (cosine similarity in [0, 1], default 0.95, over non-chunk candidates with already-linked pairs excluded, complete within the candidate set), exposed as `GET /health/store`, as a counts summary in `memory://status` and in the `consolidate()` report, and as a `### Store health` line at session start; (US4) version 0.4.0, CHANGELOG, README, roadmap (ecosystem relabelled 0.5), memory-tiers.md and the CLAUDE.md template. No new dependency, no git calls, no new MCP tool, no `--fix` mode, no warm/cold tiers or route hints.
