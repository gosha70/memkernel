# Origin: Evaluate moving to mcp 2.x

Source: https://github.com/gosha70/memkernel/issues/95 (copied 2026-11-08, verbatim)

## Issue body

memkernel pins `mcp = ">=1.25,<2"` (`pyproject.toml`, in 0.6.0 and on `main`). wiki-studio's optional MCP server (`wiki-studio[mcp]`, 0.8.0 and later) requires `mcp>=2.3,<3`. So the two cannot share one environment:
- `pip install 'memkernel[wiki]==0.6.0' 'wiki-studio[mcp]==0.8.1'` fails with `ResolutionImpossible`.
- The bridge itself needs only base wiki-studio, which has no dependency conflict.
- The README (#94) documents installing `wiki-studio-mcp` in its own environment as the workaround.

## To evaluate
- **What memkernel uses from `mcp` 1.x**, and whether mcp 2.x keeps it:
  - `mcp.server.fastmcp.FastMCP` and `Context`, used in `src/memkernel/mcp/`;
  - the stdio and streamable-HTTP transports;
  - `mcp.shared.memory.create_connected_server_and_client_session`, used by the e2e tests. This is an in-memory transport: `test_stdio_roundtrip_retain_recall_get_forget` does not start stdio despite its name, and Streamable HTTP is checked only by asserting that its setting reaches `server.run()`. So neither real transport is exercised today.
- **Whether a range spanning both majors is possible**, for example `>=1.25,<3`, or whether 2.x needs a hard move. If it needs a hard move, what that means for hosts on older MCP SDKs.
- **Host compatibility on 2.x:** Claude Code and Kiro registrations and the templates under `templates/`, and the tool set that `test_tool_count_under_10` pins.
- **A decision record in `docs/adr/`,** as `CLAUDE.md` requires for dependency changes.

## Done when
Either:
- a branch on mcp 2.x does all of the following:
  - passes the fast suite and the e2e tests;
  - passes two new end-to-end tests on mcp 2.x: a stdio roundtrip against the server started as a subprocess, and a Streamable HTTP roundtrip with a live client against the running server;
  - installs `memkernel[wiki]` and `wiki-studio[mcp]` together in one environment; or
- a short record explains why memkernel stays on 1.x for now. The two-environment install then stays the documented one.

Related: wiki-studio 0.8.1's `docs/quickstart-memkernel.md` installs `memkernel[wiki]==0.6.0` and `wiki-studio[mcp]==0.8.1` together, which hits this conflict.


## Comments

wiki-studio side: gosha70/wiki-studio#79 (merged, `3f4a24a`) fixes `docs/quickstart-memkernel.md`. It installs `memkernel[wiki]==0.6.0` with base `wiki-studio==0.8.1`, and installs `wiki-studio[mcp]` in its own environment, registered by absolute path. The `quickstart-memkernel` CI job now resolves every `pip install` line on the page with `pip install --dry-run`. If memkernel moves to `mcp` 2.x, the page can go back to one environment, and that check will confirm the combined line resolves before it ships. Nothing on the wiki-studio side is blocked meanwhile: the tested pairs in `docs/compatibility.md` use base wiki-studio.
