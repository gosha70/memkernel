## What S4 covers

From #59's Phase 2 plan ("supersede suggestions at retain; canonical hashing") and its finding D8 ("dedup is exact-hash only"):

- **Supersede suggestions at retain.** When a new memory is close to a live one of the same type (a near-duplicate, or a newer version of a decision), `retain` points that out, so the caller can pass `supersedes=<ref_id>` and the old record stops competing with the new one in recall. A suggestion only; memkernel never supersedes on its own (records are never replaced by callers implicitly, per CLAUDE.md).
- **Canonical hashing.** `content_hash` is SHA-256 of the raw UTF-8 content (`memory/dedup.py::compute_content_hash`), so text that differs only in whitespace, line endings or similar is stored twice. A canonical form before hashing would make the exact-match dedup catch those.

## The hashing caveat (decide in the spec)

Changing how `content_hash` is computed changes the hash of every existing memory. #119's H3 (the context diff, FR-004) compares the `content_hash` a run's receipt recorded with the store's current one, so after a switch it would report every older memory as "changed" though its content did not change.

#119's H1 amendment (A8, approved by the owner on 2026-11-23) has each receipt record the scheme that produced its `content_hash` (`content_hash_scheme`, today `sha256-raw`). With that, H3 can tell "hashed differently" from "content changed", so S4 no longer has to land before H3. The S4 spec still has to say:

- the new scheme's name, and how existing records are handled (rehashed in place, rehashed on read, or kept on the old scheme), given that `content_hash` also drives `find_by_hash` dedup at retain;
- that H3 compares hashes only within one scheme, and reports a scheme change as such.
