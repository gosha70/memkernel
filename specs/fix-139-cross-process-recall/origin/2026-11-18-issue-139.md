# Origin: #139 (copied 2026-11-18, verbatim)

## A running server's recall misses records that other processes wrote to its store

## What happens
A running memkernel process (the MCP server) does not find, through `recall`, records that another process wrote to the same persisted store after it started. `list_memories`, `get` and `recall(order="newest", checkpoint_only=true)` do see them, since they read metadata; relevance `recall` does not.

Other processes write to the server's store in the normal Claude Code setup:
- `post-compact.py` retains Claude Code's compaction summary as a checkpoint;
- `session-start.py` runs capture (0.9.x `main`, #134), which stores failed-then-fixed commands at startup, while the MCP server for the same session is already running;
- a second MCP server on the same store, the setup #107 asks about.

So a captured error or a compaction checkpoint written during a session cannot be recalled by relevance in that session.

## Cause (checked on `main` at `4ef72c2`, chromadb 1.5.9)
- **The dense index is cached per process.** After another process adds a record, this process's `search_dense` does not return it: not after 30 seconds, not after `collection.count()` (which does report the new record) and not after re-fetching the collection. It returns it only after this process makes a write of its own to the collection; a no-op `collection.delete(ids=[<no such id>])` is enough (about 5 ms).
- **The BM25 index is built once.** `build_service()` builds it from the store; afterwards only this process's own writes reach it.

## Reproduce
A long-lived service `A` retains five records; a subprocess `B` retains one record into the same `chroma_persist_path`; then `A.list_memories()` contains B's record, but `A._vector_store.search_dense(<B's embedding>)` and `A.recall(<B's text>)` do not, and `len(A._sparse_index)` is still `A`'s count.

## Proposed fix
Before a relevance `recall`, compare the store's record count with the count this process last saw (its own writes kept in step). When they differ, refresh the dense index with the no-op write and rebuild the BM25 index from the store. One `count()` per recall when nothing changed. A test drives a real second process, so a Chroma upgrade that changes this behaviour fails CI. An addition and a deletion by others between two recalls leave the count equal and are not detected; that is a stated limit.

Related: #107 (several stdio servers on one store), #134 (capture writes from the hook process).
