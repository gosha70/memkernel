# Origin note: splitting S8 out of the #80 spec (2026-11-03)

The owner, 2026-11-03, in their own message: "split S8. On Windows: tell me what an unlocked race between two wiki
imports can do under S8. If it only repeats work or leaves something the next import repairs, degrade like #69
(no lock, one logged warning, README note) instead of refusing. If it can leave identity tags permanently wrong,
keep the refusal. Don't push until I answer."

S8 grew in `specs/memkernel-0-7-wiki-scope/` (PR #84) over three external review passes, recorded there in
`origin/2026-11-03-review-84-4.md`, `-5.md` and `-6-windows.md`: cross-process import atomicity; lost tag updates
through fetch-and-merge metadata writes; lock identity tied to the store rather than `MEMKERNEL_STATE_DIR`; shared
`EphemeralClient`s; injected persistent clients; `update_metadata` bypassing the single tag writer. Both the
external reviewer and the DeepSeek review recommended a prerequisite spec, because S8 changes a port, the
adapter's concurrency and Windows behavior.

This spec takes the generic part: lock identity, `exclusive`, `merge_tags`, `update_metadata` refusing `tags`,
and the non-POSIX branch. The wiki-specific part stays in #84's S8: the import holding `exclusive("wiki-import",
required=True)`, reserved identity tags, `promote`, and the Windows rule for wiki identity.

Under the owner's rule, the non-POSIX branch here degrades like #69 for callers that don't require the lock
(L4); #80 requires it for wiki identity, because the race analysis there found a path to permanently wrong
identity tags.

DeepSeek on this spec (2026-11-03): PASS, 0 blocking. Applied: injected persistent clients with an empty
`chroma_persist_path`; the case-sensitivity limit; a pinning test for shared `EphemeralClient` data; lock names
restricted to constants; no timeout, deliberately; `merge_tags` raises before its read; the warning's scope; the
error's home (`core/models.py`); the README wording; a forced interleaving for SC-2. Kept as is: relying on
Chroma's key merge, guarded by the pinning test (`update_metadata` no longer carries `tags`).

The owner's decision of 2026-11-03, quoted:

> On Windows: refuse only adopt_pages (and anything else that tags an existing unowned record); ordinary wiki
> imports degrade like #69 (no lock, one warning). Change the dedup rule on every platform: a retain whose content
> matches a record carrying wiki identity tags gets its own record instead of merging into it, so retain never
> raises for that. Amend both specs, then go: push both spec PRs (no force-push) and send the two links for the
> reviewer.

Effect here: #80's import requires `exclusive("wiki-import")` only when it adopts records, and no new record needs
the `tags` lock, so that remark was removed from L3.
